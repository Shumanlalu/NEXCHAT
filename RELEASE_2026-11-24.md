# NEXCHAT coordinated release — 2026-11-24

Version: Android `1.0.9` (`versionCode 10`); backend/admin as committed on `main`.
This is an additive release. It preserves accounts, conversations, messages,
settings, API compatibility, audio/video calling and all prior security hardening.

## 1. What shipped

### Unified online/offline messaging
- Online Signal-envelope relay remains the primary transport: authenticated
  WebSocket plus long-poll, durable outbox, receipts and reconnect sync.
- Nearby transport is Bluetooth Classic RFCOMM, with BLE only as a discovery aid.
  Nothing plaintext is sent over nearby sockets.
- Each routed nearby header is Signal-encrypted for the immediate neighbour. The
  inner payload remains the original Signal ciphertext for the final recipient;
  intermediate devices never decrypt it.
- Flooding is bounded by TTL, hop limit, frame-size cap, per-peer rate limit,
  `processed_envelopes` dedupe, bounded `relay_packets`, ACKs and store-and-forward
  retry. Path selection is online-first with nearby fallback only on retryable
  online failures; online sync resumes on reconnect.

### Groups, identity and attachments
- Outgoing group content is now stamped with `conversation.groupId` at the send
  chokepoints, so relay membership checks apply and recipients map messages to
  the correct `group:*` thread. Reactions also verify group membership locally.
- Safety-number QR display/copy uses `com.google.zxing:core:3.5.3`. Identity
  changes still clear the verified marker and raise an in-app security event.
- Incoming attachment chunks must match a validated manifest/conversation and
  declared bounds. Orphan chunks are TTL-bounded and purged by `CleanupWorker`.

### Calling
- Terminal `CALL_REJECT`/`CALL_HANGUP` rows are preserved until their short TTL,
  preventing a concurrent `finishCall()` from deleting a signal before it flushes.
- Static TURN credentials are no longer published. Signed-in clients call
  `GET /v1/turn-credentials`; the server mints coturn REST API credentials with a
  one-hour expiry using `TURN_SHARED_SECRET`. The public `/v1/config` stays
  credential-free and `turnConfigured` is true only when both a TURN URL and a
  shared secret exist.

### Admin panel and backend
- Server-side maintenance/minimum-version enforcement accepts `x-app-version`
  with a `User-Agent` fallback; Android sends `x-app-version`.
- Suspended/banned users are excluded from group discovery and membership reads;
  group-add capacity checks are transactional.
- Banned accounts are reported correctly in CSV exports; search escapes LIKE
  wildcards; session expiry modal, remember-me default, route gating, in-flight
  guards, call-row binding, active-session filter, user pager clamp and rollback
  label were fixed.
- Admin device revocation, role-edit/self-disable protections, duplicate-admin
  race mapping, corrupt-config fallback and first-save config race guard added.
- Admin password reset/change operations are transactional and invalidate other
  outstanding reset tokens atomically.
- Rate limits now use a Postgres-backed `@fastify/rate-limit` store instead of
  process-local memory, so the configured limit is not multiplied across
  serverless instances. Route-specific limits remain isolated.
- Supabase migrations now include admin/analytics/RLS/rate-limit parity with
  `backend/src/schema.sql`, plus a schema-parity regression test.
- Node runtime aligned to 24.x in `package.json`, `Dockerfile` and README.

### Reported UI fixes
- Overlapping/duplicated text in Appearance and About, Profile/Display Name
  rendering, NEX ID display/copy, and unwanted connection/encryption-ready
  notifications were corrected.
- Chat scrolling now auto-sticks only near the bottom and shows a new-message
  indicator when the user is reading history.
- "Connection Test" was identified as `DiscoverScreen` → "Test server" →
  `api.serverConfig()`; there is no literal "Server Scan". Legitimate group
  controls ("Sync groups", "Private groups", "New group", "Group info") were
  retained.

## 2. Installation and upgrade

### Fresh backend / self-hosted
1. Use Node.js 24.x and PostgreSQL 16.
2. Copy `backend/.env.example` to `.env`; set `DATABASE_URL`, `JWT_SECRET`,
   `CORS_ORIGIN`, and optionally `TURN_SHARED_SECRET` plus TURN URLs in
   `ICE_SERVERS_JSON`. Leave `ADMIN_SETUP_TOKEN` unset after the first admin exists.
3. `npm ci && npm run build && npm start`. Startup applies `schema.sql`
   idempotently under an advisory lock; no destructive SQL is executed.
4. Docker users: `backend/Dockerfile` now uses `node:24-alpine`.

### Existing deployment
1. Deploy the backend first. `/v1/config` will advertise
   `nearbyRelay: "bluetooth-classic-device-local"` and `pushNotifications: false`.
2. If using TURN, set `TURN_SHARED_SECRET` in the host's secret store before the
   new Android build reaches users. Without it, calls remain STUN-only.
3. If using Supabase, apply both migrations in `supabase/migrations` before
   cutover. They are `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`
   only. Verify with `supabase migration list` and the queries in
   `supabase/README.md`.
4. Build/install Android `1.0.9`. The Room 4→5 migration drops only the
   undeclared duplicate attachment index from the earlier 3→4 schema; it does not
   delete rows. Existing encrypted local data is preserved.

### Admin
No separate frontend deployment. Open `/admin` on the same origin. Existing
admin cookies, sessions, roles and settings remain valid; sessions that are
already expired are cleaned up by the UI.

## 3. Migration and rollback

### What changes in the database
- New tables: `rate_limit_counters` and the Supabase-side admin/analytics tables.
- New columns: `users.suspended_*`, `users.banned_*`, `envelopes.priority`.
- New guard row: `app_settings.remote_config_guard`; no existing setting is
  overwritten.
- Supabase RLS is enabled and Data API grants are revoked for the new tables.

No table is dropped, no column is removed, no row is rewritten destructively, and
no paid service is required.

### Safe rollback
1. Revert the release commit and redeploy the previous backend image/function.
   The additive tables and columns are harmless to the old code.
2. Keep the previous signed APK available. Android normally refuses to install
   an older `versionCode` over `1.0.9`; do **not** uninstall the app to downgrade
   unless an operator has a verified backup of the SQLCipher database. Uninstall
   destroys local encrypted messages.
3. Supabase: there is no destructive down migration. Leave the additive tables in
   place, or have the database owner write and review a separate forward cleanup
   migration after the rollback is stable.
4. TURN: removing `TURN_SHARED_SECRET` makes `/v1/turn-credentials` return
   `available: false` and `/v1/config` report `turnConfigured: false`; it does not
   break messaging.

## 5. Known limitations

- **No real-device proof.** Bluetooth RFCOMM pairing, Airplane Mode behaviour,
  radio interoperability and three-device relay were not tested in this
  workspace. An operator with physical devices must complete the release gates
  in `UNIFIED_ONLINE_OFFLINE_ARCHITECTURE_2026-11-24.md` §10 before calling the
  release production-ready.
- **Push notifications are absent.** FCM is not integrated; `/v1/config` reports
  `pushNotifications: false`. A fully backgrounded app relies on nearby relay or
  the next active poll, not server push.
- **Presence and ephemeral delivery remain process-local.** Presence is derived
  from sockets on the current instance. Durable call/message signaling is
  unaffected because Android uses the durable outbox, but multi-instance
  realtime fan-out still benefits from a persistent single-process host or a
  shared pub/sub layer.
- **Nearby metadata is observable.** Peers can see Bluetooth address, packet
  size/timing, hop path and the neighbour-routed target ID/device ID. The inner
  message remains E2EE, but metadata is not hidden.
- **Nearby identity is claimed in HELLO.** Possession of the Signal key protects
  routing headers; manual safety-number verification remains the user-visible
  trust step. A malicious nearby peer can refuse to relay.
- **Stored packets may be retransmitted to the previous hop.** Dedupe drops the
  duplicate at the receiver; dense-mesh bandwidth waste was not measured on
  devices.
- **Wi-Fi Direct is not the primary nearby transport.** It is intentionally not
  used in this release.
- **Cached remote config can lag.** Security-relevant flags are enforced
  server-side immediately; the Android cache applies them on cold start until a
  refresh succeeds. Video calls default to disabled on a fresh install.
- **Release signing material is operator-managed.** No production-signed APK is
  included in this workspace.

## 6. Security considerations

- No custom cryptography was introduced. All message/attachment encryption uses
  the existing `org.signal:libsignal-android:0.86.5` implementation and
  SQLCipher-encrypted Room storage.
- Plaintext never reaches the relay or a nearby relay device. Only opaque Signal
  ciphertext and encrypted routing headers are transmitted.
- TURN uses the standard coturn REST API HMAC-SHA1 contract with a one-hour
  expiry. The shared secret is server-only and is never returned by
  `/v1/config`.
- Admin setup remains closed once an admin exists, uses a server-side token, and
  is protected by bcrypt cost 12 with legacy scrypt upgrade-on-login.
- Suspension/ban/device revocation are enforced server-side on every request and
  socket; clients only react to the resulting revocation signals.
- Supabase Data API access is deny-by-default for NEXCHAT tables; the relay's
  owner connection is the only application data path.
- Logs continue to redact identifiers and secrets; request bodies are never
  logged.
- Existing AGPL/licensing obligations of libsignal and SQLCipher remain the
  operator's responsibility; no mandatory paid dependency was added.
